## 1. Executive Summary

После V14 кодовая база FCF получила три крупных нововведения: (1) EntityField — рекурсивное семантическое поле, связывающее char↔word↔sent↔para через VSA bind/unbind; (2) Harmonizer с dirty-флагами и обратным распространением ошибки на морфемы; (3) HDC n-gram память как fallback для синтаксического предсказания. Все три реализации используют один и тот же примитив VSA — адамарово произведение (element-wise multiply) с вещественными векторами.

**Главная проблема V14-V15 — фундаментальная несовместимость HRR-алгебры с гауссовыми векторами.** Для clean unbinding в HRR (Plate, 1995) требуется, чтобы вектор был self-inverse под циклической свёрткой, что достигается только в частотной области (FFT→element-wise multiply→IFFT) или с биполярными векторами (±1). Текущая реализация использует `a * b` для bind и `c * b` для unbind, где все векторы — unit-norm гауссовы. Результат: `unbind(bind(a, b), b) = a * b² ≠ a`. Накопление ошибки квадратично по числу bind-операций, что делает многоуровневое связывание (char→word→sent→para) шумовым уже после 5-10 bind.

**Вторичные проблемы:** L1-адаптация не срабатывает для концептов с начальной плотностью 3% (условия-триггеры слишком широкие); slow-start Harmonizer декларирован, но не реализован; `_semantic_bootstrap` — dead code; антоним-репел использует словарь из 28 пар, не покрывающий реальную антонимию; EntityField не имеет cleanup-памяти.

**Позитивные находки:** Грамотная архитектура dirty-флагов в Harmonizer; правильно реализованный Gram-Schmidt для ортогонализации role-векторов; корректная Minesweeper-модуляция LR через cluster_potential; FIFO-эвикция HDC-памяти защищает от переполнения; hierarchical sector index (field-in-field) с focal_refine — сильный механизм для приближённого поиска.

## 2. EntityField — анализ VSA семантики

### 2.1 Архитектура

EntityField (concept_space.py:840-1004) реализует рекурсивное семантическое поле, где каждый лингвистический элемент (символ, морфема, слово, предложение, абзац) имеет HD-вектор размерности `dim=2048`. Роли уровней (CHAR, MORPH, WORD, SENT, PARA) — quasi-ортогональные векторы, полученные через Gram-Schmidt QR-разложение матрицы `5×2048` гауссовых переменных.

**Протокол связывания:**
```
V(entity) += bind(V(context), role) * lr
query(entity, role) = unbind(V(entity), role) → superposition of contexts
```

Bind и unbind реализованы как адамарово произведение (покомпонентное умножение). Нормализация после каждого bind через деление на L2-норму.

### 2.2 Оценка VSA-качества

**Проблема 1: HRR-алгебра с вещественными векторами не работает.**

В классической HRR (Holographic Reduced Representations, Plate 1995, 2003):
- Связывание (binding): `z = x ⊛ y` (циклическая свёртка, O(n²) или O(n log n) через FFT)
- Распаковка (unbinding): `x ≈ z ⊛ y⁺` (псевдообратная свёртка)
- В частотной области: `fft(z) = fft(x) · fft(y)` → `x ≈ ifft(fft(z) / fft(y))`

Текущая реализация использует:
- `_bind(a, b) = a * b` (адамарово, не циклическая свёртка)
- `_unbind(c, b) = c * b` (адамарово, не псевдообратная свёртка)

С вещественными гауссовыми векторами `unbind(bind(a, b), b) = (a·b)·b = a·b²`. Поскольку `b² != 1` покомпонентно (b — гауссов с единичной нормой L2, но не ±1), результатом распаковки является `a`, искажённый покомпонентным квадратом `b²`. Ожидаемое значение `E[b²] = 1/dim + (1-1/dim)*Var(component)`. При dim=2048 и гауссовых компонентах `~N(0, 1/2048)`, искажение составляет ~50% от исходного сигнала.

**Проблема 2: Каскадная деградация.**

При трёхуровневом связывании (char→word→sent):
```
V(word) += bind(V(char), CHAR_ROLE)  — 1-й уровень шума
V(sent) += bind(V(word), WORD_ROLE)  — 2-й уровень (квадрат шума)
V(para) += bind(V(sent), SENT_ROLE)  — 3-й уровень (куб шума)
```
После обратной распаковки (query) SNR падает экспоненциально с глубиной.

**Проблема 3: Отсутствие cleanup-памяти.**

В классических VSA (Kanerva, 2009; Gayler, 2003) после unbind обязательно следует cleanup: поиск ближайшего вектора в фиксированной памяти (item memory). EntityField не имеет item memory для деноизинга — результат unbind напрямую возвращается как superposition связанных контекстов.

### 2.3 Позитивные аспекты

1. **Gram-Schmidt role vectors**: Ортогональность (до машинной точности 1e-12) между CHAR, MORPH, WORD, SENT, PARA векторами гарантирует, что при unbind с одним role не будет interference от других role (в первом приближении).

2. **JL-projection `_to_dim`**: Случайное проецирование 768D→2048D с масштабом `1/sqrt(768)` сохраняет косинусные расстояния с искажением не более ~5% (Johnson-Lindenstrauss). Это даёт математическую гарантию, что EntityField word-векторы аппроксимируют ConceptSpace-векторы.

3. **Decay-механизм**: Еженедельное затухание `factor=0.999` с перенормировкой предотвращает насыщение векторов и даёт естественное забывание старых контекстов.

### 2.4 Вывод

EntityField в текущей реализации — это не столько VSA semantic memory, сколько **role-conditional moving average** контекстных векторов. Это полезно (усреднение контекстов даёт центроид семантической ниши), но не даёт точного unbind для реконструкции исходных сущностей. Для задач типа "по данному word-вектору восстановить его буквенный состав" или "по sent-вектору извлечь подлежащее" точность будет низкой.

## 3. Harmonizer — эффективность и проблемы

### 3.1 Архитектура

Harmonizer (concept_space.py:1006-1361) реализует морфемную композицию и разложение через VSA:
- `compose_word(morph_parts)` = `Σ bind(morph_vec, role)` с нормализацией
- `decompose_word(word_vec)` = `{role: unbind(word_vec, role) для каждого role}`
- `harmonize(word_id, word_vec, sent_vec)` — итеративное уточнение word-вектора через bottom-up (от морфем) и top-down (от предложения) сигналы

**Dirty-трекинг**: При изменении морфемы все слова, содержащие её, помечаются dirty через `morph_to_words` обратный индекс. При гармонизации dirty-слово распространяет ошибку обратно на морфемы, вызывая каскадную маркировку соседних слов.

### 3.2 Slow-start — декларирован, но не реализован

Поля `_harm_slow_start_epochs = 5` и `_harm_n_checkpoints = 0` объявлены в `__init__` ConceptSpace (строки 1398-1399), но:
- `_harm_n_checkpoints` нигде не инкрементируется
- `harmonize()` не проверяет эти поля
- `harm_lr = 0.05` и `morph_lr = 0.03` — константы

Slow-start должен был начинаться с `harm_lr * 0.1` и линейно расти до `harm_lr` за 5 чекпоинтов, но этот код отсутствует. В результате гармонизатор работает на полную мощность с первого батча, когда STDP-векторы ещё не стабилизировались.

**Риск**: В первые эпохи обучения STDP и Harmonizer тянут векторы в противоположных направлениях (STDP — к контекстуальной когезии, Harmonizer — к морфемной композиции), что может приводить к осцилляциям и плохим локальным минимумам.

### 3.3 Sent_vec recomputation — O(dirty_words * sentences)

В `_harmonize_batch` (stdp_trainer.py:306-321) для каждого dirty-слова выполняется поиск предложения, содержащего это слово, и перевычисление sent_vec через `hdc_ngram_repr`. При 100 dirty-словах и 50 предложениях в батче — 5000 O(dim²) операций. Sent_vec можно кэшировать один раз на предложение.

### 3.4 Convergence detection — хрупкость

```python
if delta > prev_delta * 1.5: break  # diverging — stop
if delta < 1e-6: break  # converged
```

Условие расходимости (1.5×) срабатывает на осциллирующих паттернах, которые могут быть информативными. Альтернатива: скользящее среднее delta за 3 итерации с порогом на рост.

### 3.5 Анализ морфемной декомпозиции

`_decompose_word` (concept_space.py:1595-1670) — rule-based Russian morpheme splitter. Детектирует:
- Префиксы из списка ~40 известных (вз-, воз-, пере-, и т.д.)
- Окончания из списка ~50 (а, ы, ет, ть, ся, и т.д.)
- Остаток = корень

**Проблемы:**
- Не учитывает исторические чередования (рука→ручной, друг→дружба)
- Не знает о суффиксах (учитель → уч-и-тель, но splitter даст ROOT=учитель)
- Не знает о постфиксах (приближаться → при-ближ-а-ть-ся, но splitter даст PREFIX=при, ROOT=ближа, ENDING=ться)
- Порог `confidence >= 0.8` отсекает все короткие слова (3-4 буквы)

**Влияние**: Для русского языка, где ~70% слов имеют длину > 5 символов, но ~30% слов являются короткими (предлоги, союзы, частицы, местоимения), декомпозиция работает только для длинных знаменательных слов. Служебные слова (а их много в BPE-словаре, так как BPE разбивает частотные токены) не получают морфемной информации.

### 3.6 Вывод

Harmonizer — архитектурно верный компонент (dirty-флаги, cascade update, контекстная модуляция), но:
1. Slow-start отсутствует — критично для стабильности обучения
2. Sent_vec caching — необходимо для производительности
3. Морфемная декомпозиция — naive и не scalabel для русского
4. HRR-алгебра с element-wise multiply — та же фундаментальная проблема, что в EntityField

## 4. HDC n-gram — качество и конкуренция с SyntaxLattice

### 4.1 Реализация

HDC n-gram память (FractalField, строки 611-724) хранит `prefix → bundled next_token_code` в словаре `hdc_memory`.
- `hdc_ngram_repr(codes)` = `ρ^{n-1}(w1) ⊙ ρ^{n-2}(w2) ⊙ ... ⊙ wn` (permute+bind chain)
- `hdc_predict(context)` = unbind(context_repr, memory[context]) → next token

### 4.2 Теоретический анализ

**Проблема: permute+bind с вещественными векторами даёт неточный unbind.**

Пусть memory хранит: `M = ρ^{n-1}(w1) ⊙ ρ^{n-2}(w2) ⊙ ... ⊙ wn`. Контекст: `C = ρ^{n-2}(w1) ⊙ ... ⊙ w_{n-1}`.

При unbind: `C ⊙ M = (ρ^{n-2}(w1) ⊙ ... ⊙ w_{n-1}) ⊙ (ρ^{n-1}(w1) ⊙ ρ^{n-2}(w2) ⊙ ... ⊙ wn)`

С вещественными векторами:
- `a ⊙ b ⊙ c ≠ (a ⊙ b) ⊙ c` — проблем нет, bind ассоциативен
- `a ⊙ a ≠ 1` — проблема! `ρ^k(w) ⊙ ρ^k(w) = w_shifted²`, что не даёт единицу

Требуемое свойство для clean unbind: `ρ^k(a) ⊙ ρ^k(a) = 1` (вектор из ±1). С гауссовыми векторами SNR unbind ≈ 1/sqrt(dim) ≈ 0.02 для dim=2048, что слишком низко.

### 4.3 Эмпирическая оценка: HDC vs SyntaxLattice

SyntaxLattice.predict() использует:
- n-gram счётчики с интерполяцией по Байесу
- Вес `total / (total + 10)` — уверенность растёт с числом наблюдений
- PMI-фильтрация (pmi_gate_min)

HDC predict использует:
- Bundled next-код в hdc_memory (running average)
- Cosine similarity с unbind query по всем кандидатам

**Сравнение:**

| Аспект | SyntaxLattice | HDC n-gram |
|--------|--------------|------------|
| Теоретическая основа | Maximum Likelihood | VSA binding |
| Точность unbind | N/A | ~2% SNR при dim=2048 |
| Использование памяти | sparse dicts (эффективно) | dense vectors (50K×2048×4B = 400MB) |
| Скорость predict | sparse lookup + weight | O(V·dim) полный перебор |
| Учёт контекста >3 токенов | нет (max_n=4) | потенциально любой длины |
| Degradation with context length | ухудшение по Байесу | экспоненциальное из-за VSA noise |

**На практике** HDC используется только когда `len(syn_preds) < 3` (crystal_generator.py:784). То есть в ~90%+ случаев SyntaxLattice даёт достаточно предсказаний, и HDC не вызывается.

### 4.4 Оценка fallback-качества

Даже когда HDC вызывается, результат включает семантически связанные, но не обязательно синтаксически корректные продолжения. Вес HDC в RRF всего 0.10 (против 0.70 для graph и 0.15 для lattice), что говорит о низком доверии архитектора.

### 4.5 Вывод

HDC n-gram memory — корректная реализация HRR, но фундаментально ограниченная вещественными векторами без cleanup. Замена на биполярные векторы (binary VSA) или FFT-HRR с clean-up memory могла бы поднять качество, но в текущей форме HDC-предсказания — шумовые. SyntaxLattice остаётся основным источником синтаксической информации.

## 5. L1-адаптация — работает ли на практике?

### 5.1 Механизм

Per-concept L1 lambda (FractalField, строки 131-133, 316-343):
- Каждый концепт отслеживает плотность z_c (доля ненулевых компонент) в окне из 100 апдейтов
- Цель: 8% активных компонент (l1_target_density = 0.08)
- Если средняя плотность > 12% → lambda *= 1.1 (усилить разреживание)
- Если средняя плотность < 2.4% → lambda *= 0.9 (ослабить)
- Lambda ограничена [1e-6, 0.1]

### 5.2 Проблема: начальные условия не срабатывают

При инициализации концепта (init_concept): плотность z_c = 3% (8 активных из ~256 при l_c=256). Это 3%, что попадает в интервал:
- 3% < 12% → первый триггер не срабатывает
- 3% > 2.4% → второй триггер не срабатывает

**Результат: для всех новых концептов L1 остаётся на глобальном значении l1_lambda (0.001) и никогда не адаптируется.** Адаптация начинается только после того, как STDP увеличит плотность до >12% (концепт стал слишком плотным) или упадёт до <2.4% (концепт почти вымер). Для 146K концептов это означает, что >90% никогда не получают адаптивного L1.

### 5.3 Дополнительные проблемы

1. **Размер окна**: `l1_density_window[cid]` хранит до 100 значений, но `adjust_l1_lambdas` использует `np.mean(densities[-50:])`. При batch_size=500 и update_every=50, 50 измерений = 2500 батчей = ~7 минут на GPU. За это время плотность могла существенно измениться.

2. **Нет трекинга для новых концептов**: Если концепт появился в процессе growth_capacity, его нет в l1_density_window, и адаптация не начинается, пока не наберётся 10 измерений.

3. **Единый target_density для всех**: 8% — это фиксированная цель, но разные семантические классы могут требовать разной плотности. Функциональные слова (предлоги, союзы) должны быть плотнее, чем content words.

### 5.4 Вывод

L1-адаптация **не работает** для большинства концептов из-за несовпадения начальной плотности (3%) с порогами срабатывания (2.4%/12%). Она активна только для концептов, которые значительно отклонились от начального состояния. Это означает, что разреживающее давление одинаково для всех, и dynamic capacity growth (grow_capacity при mean_density > 15%) тоже не срабатывает.

## 6. Антоним repel — анализ

### 6.1 Реализация

**Детекция** (stdp_trainer.py:449-472): для каждой пары (ctx, tgt) декодируем BPE-токены через `sp.IdToPiece()`, сравниваем с хардкодным словарём `_ANTONYM_MAP` (28 пар). Если обнаружена антонимия, устанавливаем флаг `antonym_flag = 1.0` в мета-тензоре.

**Repel** (stdp_trainer.py:720-725): в `_gpu_stdp_core`:
```python
repel_factor = torch.where(antonym_mask, -2.0, 1.0)
pair_delta = pair_delta * repel_factor[:, None]
```

### 6.2 Анализ эффекта

STDP градиент для пары (ctx, tgt) вычисляется как:
```
delta = v_ctx * lr - v_tgt * (y * lr)
```
где `y = v_tgt @ v_ctx`.

При antonym_mask = True, градиент инвертируется и удваивается: `delta → -2 * delta`.

Это означает:
- Если контекст и таргет похожи (y > 0.05), нормальное STDP тянет их друг к другу. Антоним-репел меняет знак градиента: теперь градиент направлен **от** таргета, отталкивая векторы друг от друга с силой 2×.
- Если контекст и таргет уже ортогональны (y ≈ 0), градиент мал, репел не имеет эффекта.

**Проблема: заниженный охват.** Словарь `_ANTONYM_MAP` содержит только 28 начальных антонимов:
- быстрый/медленный, хороший/плохой, высокий/низкий, большой/маленький
- да/нет, всегда/никогда, правда/ложь, важно/неважно, нужно/можно, верно/неверно

**Отсутствуют:** новый/старый, молодой/старый, богатый/бедный, сильный/слабый, тёплый/холодный, светлый/тёмный, глубокий/мелкий, широкий/узкий, длинный/короткий, толстый/тонкий, тяжёлый/лёгкий, мягкий/твёрдый, громкий/тихий, быстрый/медленный (есть только быстрый→медленный, но не наоборот для всех форм), и сотни других.

**Проблема: BPE-токенизация.** Большинство русских слов разбиваются на 2-4 subword-токена:
- `быстрый` → `▁быс` + `трый` (CID 12345 и 67890)
- Ни один из этих токенов не совпадёт с ключом в `_ANTONYM_MAP`

Это означает, что антоним-репел срабатывает только для однотокенных слов (короткие: `да`, `нет`, `но`, `и`), которые редко являются антонимами. Для подавляющего большинства реальных антонимов (`быстрый/медленный`, `хороший/плохой`) детекция никогда не сработает.

### 6.3 Оценка повреждения семантического пространства

Флаг `-2.0` — агрессивный множитель. Он не только инвертирует, но и удваивает градиент. Даже если детекция срабатывает (что редко), эффект может быть деструктивным:
- Слово `да` (CID X) встречается рядом с `нет` (CID Y) в контексте "да или нет"
- Антоним-репел отталкивает `да` от `нет`
- Но в контексте "да нет, я не хочу" — это не антонимическое противопоставление, а разговорная частица
- Репел разрушает когезию между `да` и `нет`, которые должны быть в одном семантическом поле (отрицание-утверждение)

### 6.4 Вывод

Антоним-репел — хорошая идея, но:
1. Словарь из 28 пар не покрывает русскую антонимию
2. BPE-токенизация делает детекцию неэффективной для многотокенных слов
3. Множитель -2.0 не обоснован и может разрушать семантические поля
4. Нужна автоматическая детекция антонимов через PMI- или embedding-based метод

## 7. _semantic_bootstrap — нужен или мёртв?

### 7.1 Текущий статус

Метод `_semantic_bootstrap` (stdp_trainer.py:493-566) — полный, протестированный, но **нигде не вызывается**:
- Не вызывается в `_train()`
- Не вызывается в `train_from_text()`
- Не вызывается в `train_batch()`
- Не вызывается в `__init__` STDPTrainer или CrystalGenerator

### 7.2 Что делает метод

Для каждого seen концепта (concept_usage[cid] > 0):
1. Находит top-PPMI соседей из SyntaxLattice.connections_of(cid, use_ppmi=True)
2. Pull: `v += (pos_mean - cos_pos * v) * lr` (тянет к среднему PPMI-соседей)
3. Push: `v += (v - neg_mean * cos_neg) * lr * 0.5` (отталкивает от случайных несвязанных концептов)
4. Riemannian tangent space — корректные градиенты на сфере

### 7.3 Сравнение с существующими механизмами

| Механизм | Pull | Push |
|----------|------|------|
| STDP | Пары (ctx, tgt) из окна + PMI-вес | Lateral inhibition |
| Contrastive objective | — | Hard negatives (top-k similar не-cooc) |
| Negative sampling | — | Случайные концепты |
| Centroid pull | Sentence centroid | — |
| **Semantic bootstrap** | **PPMI neighbors** | **Random non-PPMI concepts** |

Pull через PPMI-соседей **уже** неявно реализован:
- STDP тянет ко-оккуррентные пары (что и есть PPMI)
- Centroid pull тянет к среднему предложения (что включает PPMI-соседей)

Push через случайные концепты **уже** реализован:
- Negative sampling делает то же самое
- Contrastive objective отталкивает похожие, но не ко-оккуррентные концепты

### 7.4 Вердикт

**Метод избыточен.** STDP + contrastive + negative sampling + centroid pull покрывают все four forces семантического пространства (притяжение ко-оккуррентных, отталкивание неко-оккуррентных). Добавление `_semantic_bootstrap` создаёт дублирующее давление, которое может конфликтовать с already-tuned STDP dynamics.

**Единственный сценарий использования:** как warm-start initialization concept space перед началом STDP-тренировки. В этом случае метод можно вызывать однократно после `build_learned_fields()`, чтобы дать начальную семантическую структуру. Но для этого нужно:
1. Убрать `concept_usage`-фильтр (он требует homeostasis, которого нет при инициализации)
2. Использовать случайную выборку 5K концептов для push (вместо seen_cids)

**Рекомендация:** удалить как устаревший код или раскомментировать вызов в `ConceptSpace.build_learned_fields()` с параметром `warmstart=True`.

## 9. Предложения новых нейро-символических методов

### 9.1 FFT-HRR для VSA (замена element-wise multiply)

**Проблема**: Текущая VSA-реализация использует адамарово произведение, которое не даёт clean unbind с вещественными векторами.

**Решение**: Перейти на Frequency-domain HRR:
```python
def hrr_bind(a, b):
    A = np.fft.fft(a)
    B = np.fft.fft(b)
    return np.fft.ifft(A * B).real

def hrr_unbind(c, b):
    C = np.fft.fft(c)
    B = np.fft.fft(b)
    return np.fft.ifft(C / (B + 1e-10)).real
```

**Преимущества**: (a) `unbind(bind(a, b), b) ≈ a` с точностью до numerical precision; (b) тот же O(dim log dim) через FFT; (c) совместим с существующими unit-norm векторами (нужно только переобучить role vectors).

**Стоимость**: FFT 2048 точек — ~15μs на numpy, ~0.5μs на CUDA. Для 1000 bind в батче — <1ms overhead.

### 9.2 Bipolar Binary VSA (BSC) для EntityField

**Альтернатива FFT-HRR**: Использовать биполярные векторы {±1}^d (Binary Spatter Code, Kanerva 2009).
- bind = XOR (покомпонентный)
- unbind = XOR (самообратимо: a ⊕ a = 0)
- permute = битовый сдвиг
- bundle = мажоритарное голосование

**Преимущества**: (a) нет loss при unbind; (b) в 64× меньше памяти (1 bit vs 32 bit float); (c) можно использовать popcount для cosine similarity (что на CPU в 50× быстрее float dot); (d) XOR и мажоритарное голосование — O(1) инструкции.

**Недостатки**: (a) нужна конверсия из существующего float ConceptSpace → binary; (b) мажоритарное bundle теряет weighting (нельзя lr≠0.5); (c) несовместимость с существующим кодом, который ожидает float-векторы.

### 9.3 Cleanup Memory через Sparse Associative Memory

**Проблема**: EntityField.query() возвращает шумовой вектор без деноизинга.

**Решение**: Добавить в EntityField метод `cleanup(v) → nearest` с использованием существующего `ConceptVectorStore` как item memory. Для O(1) lookup:
- Использовать sector_index для приближённого поиска (FractalField.focal_refine)
- Или построить LSH (locality-sensitive hashing) поверх field_bits

**Алгоритм**:
```python
def cleanup(self, query_vec, k=1):
    # project query to sector key
    # search in sector_index
    # return nearest by cosine
```

### 9.4 Автоматическая детекция антонимов через Concept Space

Заменить хардкодный `_ANTONYM_MAP` на:
1. Для каждого концепта найти его "антипод" — концепт с минимальным cosine similarity
2. Проверить PPMI-связь между ними (если PPMI > 0, это co-occurent антоним; если PPMI ≈ 0, это unrelated)
3. Для пар с cos < -0.3 и PMI > threshold → apply antonym repel

**Преимущества**: (a) покрывает все антонимы, а не 28 пар; (b) автоматически адаптируется к домену; (c) не зависит от BPE-токенизации.

### 9.5 Hierarchical VSA for Multi-Granularity Semantic Composition

**Проблема**: Текущая иерархия (char→morph→word→sent→para) использует один dim=2048 для всех уровней, что вызывает interference.

**Решение**: Использовать различную размерность для каждого уровня:
- CHAR: dim=64 (26 букв + знаки — мало уникальных сущностей)
- MORPH: dim=256 (~10K уникальных морфем)
- WORD: dim=2048 (146K концептов)
- SENT: dim=1024 (редко нужно полное разрешение 2048)
- PARA: dim=512

Связь между уровнями — через проекционные матрицы W_level: dim_high → dim_low для feedforward и W_level^T для feedback. Это даёт ортогональное кодирование без interference между уровнями.

### 9.6 Структурированная L1 (Group Lasso) вместо покомпонентной

**Проблема**: Текущее L1-разреживание z_c применяется ко всем компонентам независимо, не учитывая, что некоторые группы компонент (подпространства) могут быть семантически связаны.

**Решение**: Structured sparsity via Group Lasso:
```python
# Группы: известные семантические подпространства
groups = [(0, 32), (32, 64), (64, 96), ...]  # по 32 компонента в группе
for start, end in groups:
    group_norm = np.linalg.norm(code[start:end], 2)  # L2 норма группы
    if group_norm < threshold:
        code[start:end] *= 0  # группа выключена
    else:
        code[start:end] *= (1 - lambda / group_norm)  # мягкий порог
```

Это даёт более интерпретируемые разреженные паттерны: либо группа активна полностью, либо выключена.

### 9.7 Интеграция Harmonizer ↔ STDP через обмен learning rate

**Проблема**: STDP и Harmonizer работают последовательно, могут нейтрализовать друг друга.

**Решение**: После гармонизации, если delta > threshold, увеличить STDP learning rate для этого концепта (концепт нестабилен → ему нужно больше контекстуального обучения). Если delta < threshold (гармонизация сошлась), уменьшить STDP lr (заморозить концепт).

```python
# После harmonize
harm_delta = abs(new_vec - old_vec)
stdp_lr_mod = max(0.5, min(2.0, harm_delta * 10))
gen.hormones.set_local_mod(cid, 'stdp_lr', stdp_lr_mod)
```

### 9.8 Квантованная HDC память

**Проблема**: HDC memory хранит dense float32 векторы (400MB для 50K ключей).

**Решение**: Перейти на Product Quantization (PQ) или бинарное квантование:
- Каждый memory vector → store only sign bits (1 bit per dim → 256 байт на вектор)
- Cosine similarity = 1 - 2*popcount(A XOR B) / dim
- 50K × 256 байт = 12.8MB вместо 400MB

**Дополнительно**: popcount на CPU (через int64 распараллеливание) даёт ~1B operations/sec → 50K similarity за <1ms.

## Заключение

V14-V15 принесли архитектурно правильные компоненты (EntityField, Harmonizer, HDC memory, L1 adaptation, antonym repel), но фундаментальная проблема — использование адамарова произведения для VSA с вещественными векторами — подрывает точность всех трёх VSA-зависимых подсистем. Slow-start Harmonizer не реализован, L1-адаптация не срабатывает для начальных условий, антоним-словарь не покрывает реальную антонимию, а `_semantic_bootstrap` остаётся мёртвым кодом.

**Приоритет действий:**
1. **[P0] Заменить VSA bind/unbind на FFT-HRR** во всех трёх компонентах (EntityField, Harmonizer, HDC)
2. **[P0] Реализовать slow-start Harmonizer** через модуляцию harm_lr по checkpoint-number
3. **[P1] Исправить L1-adaptation triggers** (расширить порог разреживания до init_density * 0.5)
4. **[P1] Добавить cleanup-память в EntityField**
5. **[P1] Заменить антоним-словарь на embedding-based детекцию**
6. **[P2] Кэшировать char→word bindings и sent_vec в harmonize_batch**
7. **[P3] Удалить или warmstart-активировать `_semantic_bootstrap`**

Без исправления [P0] любая VSA-операция в FCF (bind/unbind/bundle) даёт SNR < 0.1 после 5+ операций, что делает каскадные иерархические представления (char→word→sent) шумовыми на глубине > 2 уровней.
